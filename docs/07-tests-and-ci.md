## CI/CD (`.github/workflows/ci-cd.yml`)

Token permissions are `{}` at workflow level. Each job requests only what it needs: `build-test` gets `contents: read` and `pull-requests: read` (gitleaks lists the PR's commits); `deploy` gets `contents: read` and `id-token: write` (OIDC). Timeouts: 30 minutes for `build-test`, 60 minutes for `deploy`. GitHub-owned actions (`actions/*`, `github/*`) are pinned by major version; every other action is pinned to a full commit SHA with a version comment, and Dependabot updates both.

Pipeline stages, all required before deployment:

1. **Secret scan** (gitleaks, pinned to a commit) runs first — before any pull-request code executes, so that code cannot plant a `.gitleaksignore`, and regardless of later test results. Pushes and pull requests scan only their new commits; a manual dispatch (the deploy path) scans the full history. `.gitleaksignore` holds the reviewed false positives from the initial commit as exact `commit:file:rule:line` fingerprints, so nothing new can match it; changes to it need CODEOWNERS review.
2. **Start Azurite**: `docker run mcr.microsoft.com/azure-storage/azurite:3.37.0 ... --skipApiVersionCheck --disableTelemetry`, bound to `127.0.0.1`, then wait until Azurite answers HTTP on ports 10000/10001. A service container is not used because Azurite needs the `--skipApiVersionCheck` flag. Azure.Storage.Blobs 12.30.1 sends service API version 2026-10-06, which no Azurite release supports yet; without the flag even 3.37.0 returns `400 InvalidHeaderValue` (verified 2026-10-16).
3. **Restore with NuGet Audit**, configured in `Directory.Build.props` (`NuGetAuditMode=all`, `NuGetAuditLevel=low`). When `CI=true`, NU1901–NU1904 (known vulnerabilities) and NU1900/NU1905 (vulnerability data unavailable) are errors, so restore fails closed on any known vulnerable direct or transitive package; locally they are warnings. Dependabot (`.github/dependabot.yml`) proposes NuGet and GitHub Actions updates weekly.
4. **Build** (`dotnet build -c Release`, nullable warnings are errors).
5. **Host-extension vulnerability check**: the Functions SDK restores a generated `WorkerExtensions` project (the host-side extensions that ship to Azure) without `Directory.Build.props`, so NuGet Audit settings never reach it. CI runs `dotnet list package --vulnerable --include-transitive --format json` on it and fails on any finding — or if no report can be produced.
6. **Unit + integration tests**; failures fail the job. The integration step sets `ADR_TEST_REQUIRE_AZURITE=true`, so Azurite tests fail instead of silently skipping. TRX results and coverage are uploaded as the `test-results` artifact. They are not published as a check run: that needs `checks: write`, which pull requests from forks never get.
7. **Bicep validate**: `az bicep build` + `az bicep lint`.
8. **Contract docs freshness**: regenerates `docs/03-mcp-contracts.md` and diffs.
9. **Publish artifact** (`api`) for traceability.
10. **Deploy job** runs on a `main` push or manual dispatch from `main`, and only when the repository variable `ADR_DEPLOY_ENABLED` is `true` (explicit opt-in, so forks and fresh clones never deploy). Without it, a push to `main` emits a `Deploy skipped` notice and the run stays green; with it, a preflight step fails loudly if any required Azure variable is empty. A push deploys only when it changes something that ships: if every changed file is under `docs/`, `tests/`, `samples/`, `tools/`, `.vscode/`, `.claude/` or `.github/`, a Markdown file, `LICENSE`, `.gitignore`, `.gitattributes` or `.mcp.json`, the deploy job is skipped with a `Deploy skipped` notice and no approval is requested (an unanswered approval would hold the environment and queue every later deploy behind it). A change to `ci-cd.yml` itself, any other path, or an unknown base commit (first or force push) deploys; a manual dispatch always deploys. The deploy job runs on `ubuntu-24.04` (pinned) so a runner-image change reaches the build job first. The job uses a **protected GitHub environment** (required reviewers = human approval gate) and **OIDC federated identity** (`azure/login` + `azd auth login --federated-credential-provider github`) — no long-lived Azure credentials. One deployment per environment runs at a time; a running deployment is never cancelled. It runs `azd provision --preview` (the what-if plan, resolved from the same parameters; provision hooks are skipped) before `azd provision` and `azd deploy`; `azd deploy` is retried up to 3 times because the app identity's role on the deployment container can still be propagating on a first deployment.
11. **Wait for start**: polls the anonymous `/api/health` probe for up to 5 minutes. A worker that never starts usually means an unresolved Key Vault reference for `Adr__PrincipalHashSalt` (the app refuses to start with a placeholder salt). In Entra mode the probe returns 503 if the worker does not see App Service Authentication, so a deployment that would reject every call fails here.
12. **Post-deployment smoke test** (FunctionKey mode) with the system key polled until the host has created it, held in a masked variable and passed to the script through `ADR_MCP_KEY` (never on the command line). In EntraBuiltIn mode the job instead asserts that an unauthenticated POST to the MCP endpoint returns 401 (the webhook is `Anonymous`, so App Service Authentication is the only gate), then emits a notice to run the tool smoke test manually with `ADR_MCP_BEARER=<token>`.

`scripts/setup-adr-deploy.ps1` does all of the following in one re-runnable step (PowerShell 7 or Windows PowerShell 5.1, with the Azure CLI and GitHub CLI; Azure Cloud Shell has both). It signs in with a device code if needed, limits the Role Based Access Control Administrator assignment to the roles in `infra/modules/rbac.bicep`, and creates no secrets: `.\scripts\setup-adr-deploy.ps1 -SubscriptionId <id> [-TenantId <id>] [-Location southcentralus]`. Re-runs are safe: once the repository variables exist they pin the deployment. The script signs in to the tenant in `AZURE_TENANT_ID` (device code), stops if the app in `AZURE_CLIENT_ID` is not visible there instead of creating a second one, refuses a different subscription or region, keeps `ADR_AUTH_MODE` and `ADR_PRIVATE_NETWORKING`, leaves an environment that already has reviewers and a branch policy alone, and removes any Role Based Access Control Administrator assignment that lacks the condition. It ends by reading the federated credential, role assignments, environment and variables back and prints `PASS`, or stops with what failed.

Required configuration, in this order (GitHub auto-creates a missing environment **without** protection rules, so create it first):
1. GitHub environment `adr-dev` with required reviewers and a deployment branch policy of `main` only.
2. An Entra app registration (or user-assigned managed identity) with a federated credential whose subject is exactly what GitHub issues for the `adr-dev` environment (issuer `https://token.actions.githubusercontent.com`, audience `api://AzureADTokenExchange`), holding **Contributor** plus **Role Based Access Control Administrator** (ideally constrained to the role IDs assigned in `infra/modules/rbac.bicep`) on the target subscription — the template deploys at subscription scope and creates role assignments. Repositories created after 2026-07-15 get immutable subjects, `repo:<owner>@<owner-id>/<repo>@<repo-id>:environment:adr-dev`; older ones use `repo:<owner>/<repo>:environment:adr-dev`. `gh api repos/<owner>/<repo>/actions/oidc/customization/sub` shows the prefix in use (`sub_claim_prefix`); a mismatch fails `azure/login` with `AADSTS700213`, and re-running the setup script corrects it.
3. Variables `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, `AZURE_LOCATION` (repository or `adr-dev` environment level), optional `ADR_AUTH_MODE` (`FunctionKey` default; `EntraBuiltIn` also requires `ADR_ENTRA_CLIENT_ID` and `ADR_ENTRA_ALLOWED_CLIENT_IDS`, see docs/05), `ADR_ENTRA_TENANT_ID`, `ADR_ENTRA_VALIDATE_IN_APP` (default `false`, see docs/11), `ADR_ENTRA_RESOURCE_URI`, `ADR_PRIVATE_NETWORKING`.
4. Last, the **repository** variable `ADR_DEPLOY_ENABLED=true` (it must be repository-level: the job-level `if` cannot see environment variables).
