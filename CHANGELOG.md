# Changelog

All notable changes to this project are documented here. The format follows Keep a Changelog and the project uses Semantic Versioning. Versions below 1.0.0 are pre-production: any release may change behaviour or configuration, and the upgrade steps are listed with each release.

## [Unreleased]

### Added
- [Entra sign-in checklist](docs/12-entra-sign-in-checklist.md): the owner's tick-off list for the tenant half of [issue #27](https://github.com/saulpatinojr/Proj-Cloud_Architect_Sidekick_MCP/issues/27), in order: decisions, Entra ID P1 and Conditional Access MFA for the tenant (decided 2026-10-28), a read-only look at the dev environment, the sandbox runbook, a staging deployment, each client's sign-in, close-out. Records that CI will also call the server, which needs an application app role in a later pull request. Nothing in it is done yet.
- [ADR-0010](docs/adr/ADR-0010-obsidian-second-brain.md) (Proposed): an Obsidian vault as optional context, through a standalone local read-only MCP server with no dependency on this repository; integration level A (the client connects to both servers) needs no server change, level B (tagged notes uploaded through the existing evidence path) is opt-in. Owner decisions recorded 2026-10-28: standalone in both directions, Claude Code and Claude Desktop, Obsidian Sync across machines (so the allow-list lives in a note inside the vault), read-only, and the phone as a client. The phone needs phase 2: the same read-only server hosted as its own Azure Functions app (workload `vault`, ADR-0009 names, ADR-0008 sign-in) over a Blob copy of the allow-listed folders pushed by a sync plugin; Obsidian Sync cannot be read from Azure. The code will live under `src/VaultMcp/` with its own solution file. No code is added by this ADR.
- One Azure naming convention for the resource group, every resource and the tags ([ADR-0009](docs/adr/ADR-0009-azure-naming-convention.md), Proposed): `<abbreviation>-<workload>-<environment>-<region code>-<nn>`, for example `rg-adr-dev-scus-01`, `func-adr-dev-scus-01`, `kv-adr-dev-scus-01` and `stadrdevscus01`. New Bicep parameters `workloadName` (default `adr`), `environmentShort` (default `dev`) and `nameSuffix` (default empty; appended to the four globally unique names only), set by the azd variables `ADR_WORKLOAD_NAME`, `ADR_ENVIRONMENT_SHORT` and `ADR_NAME_SUFFIX` (the last is also passed through the deploy job from a repository variable). `infra/region-codes.json` holds the region short codes (16 Flex Consumption regions); another region stops the deployment with a message, and `scripts/setup-adr-deploy.ps1` refuses it early. Bicep also stops, before anything is created, on a name part that is not lower-case letters and digits, on an `environmentName` that does not end with `-<environmentShort>` (it catches a second azd environment that was given no short name of its own) and on a Key Vault name over 24 characters.
- `ResourceNamingTests` (unit tests): the abbreviations equal Microsoft's published list, and the real `infra/main.bicep`, evaluated offline with `bicep snapshot` for every region, produces names that follow the pattern and the Azure length and character rules and carry the documented tags. CI installs Bicep before the unit tests and sets `ADR_TEST_REQUIRE_BICEP=true`, so a missing CLI fails the run instead of skipping the tests.
- [Replacing the dev environment after the naming change](docs/05-local-dev-and-deploy.md#replacing-the-dev-environment-after-the-naming-change): the owner's steps to delete `rg-adr-dev` and create `rg-adr-dev-scus-01`.
- Entra sign-in, code half of [issue #27](https://github.com/saulpatinojr/Proj-Cloud_Architect_Sidekick_MCP/issues/27) ([ADR-0008](docs/adr/ADR-0008-entra-oauth-sign-in-for-mcp-clients.md), Proposed; **off by default**, so merging it changes no deployment): with `Auth__Entra__ValidateBearerToken=true` (needs `Auth__Mode=EntraBuiltIn`) the app verifies the `Authorization` bearer token on every tool call itself, in addition to App Service Authentication at the edge, and builds the principal only from the verified token (`X-MS-CLIENT-PRINCIPAL` is no longer read). RS256 only, key chosen by `kid` from a cached tenant key set, exact v2.0 issuer, `tid`, audience = the server app's client ID, token version 2.0, both `exp` and `nbf`, an allowed client application (`azp`), the `user_impersonation` scope, and a mapped ADR app role. Signing keys that cannot be fetched give a retryable `AUTH_UNAVAILABLE` (HTTP 503), never acceptance. Logs carry a fixed reason code only. Signature and claim checks use `Microsoft.IdentityModel.JsonWebTokens` 8.23.0.
- `GET /.well-known/oauth-protected-resource` (and the path-inserted `/runtime/webhooks/mcp` form): protected resource metadata (RFC 9728) for MCP clients, as the MCP authorization spec revision 2026-07-28 requires. `GET /api/auth/check`: the same token checks with the spec's `WWW-Authenticate` challenges (401, 403, 503 with `Retry-After`) so the policy can be proven with `curl`. Both answer 404 while the switch is off.
- Bicep parameters `entraValidateInApp` (default `false`) and `entraResourceUri`, azd variables `ADR_ENTRA_VALIDATE_IN_APP` and `ADR_ENTRA_RESOURCE_URI`, passed through the deploy job.
- `scripts/entra/` holds the app roles, the delegated scope and the Azure CLI pre-authorization the runbook creates; `EntraDefinitionTests` fails if a role value equals the scope value (Entra keeps both in one collection) or if the files, the code defaults and Bicep drift apart.
- [Entra sign-in](docs/11-entra-sign-in.md): settings, reason codes, what is and is not verified, and a PowerShell real-tenant runbook. Nothing in it has been run against a tenant.
- `adr_import` tool (Approver): loads existing decisions in their current lifecycle status, keeping their ids and original decision dates. Never overwrites (same content is `unchanged`, different content is `conflict`), supports `dryRun`, 25 records per call, original Markdown kept as the source of record, provenance `adr_import`. New permission `AdrImport` (Approver, Admin).
- `tools/AdrMcp.Import`: `scan` reads a folder of ADR Markdown files and writes a staging folder with a data-quality report, `overrides.json` for human decisions and `overrides.suggested.json`; `load` sends the staged records through `adr_import`. See [Importing existing ADRs](docs/10-legacy-adr-import.md).
- ADR Markdown parser reads the Tyree and Akerman layout and the older HCW layouts: leading metadata table (ID, Status, Author, Reviewed By, Date), numbered headings, options tables, a `## Status` section, "Superseded by" status text, assumptions and constraints (kept in the context).
- `adr_get` provenance now includes `source` (for example `adr_import`).

### Changed
- **Resource names and tags (replace the dev environment).** Azure cannot rename a resource group or most resources, so the existing `rg-adr-dev` and its resources (named with a hash token, for example `func-adr-<token>`) are replaced by the new names; the function app's host name changes to `func-adr-dev-scus-01.azurewebsites.net`, so every client URL changes, and in `EntraBuiltIn` mode so does the Application ID URI of the server's Entra app registration. The Cosmos DB data, the evidence blobs and the generated principal-hash salt of the old environment are not kept. Abbreviations come from Microsoft's published list: the App Service plan is `asp` (was `plan`) and the Cosmos DB account is `cosno` (was `cosmos`). Tags are now `workload` (`adr`; it was `adr-mcp`), `application` (`adr-mcp`), `environment`, `component` and `azd-env-name`. Private endpoints and subnets are named by the same pattern; the private DNS zone link takes the virtual network's name. The azd environment name (`adr-dev`), the GitHub environment and the OIDC credential do not change.
- Markdown parsing no longer treats lines inside code fences as headings or metadata.
- `AUTH_UNAVAILABLE` (retryable) is a new failure code in every tool's contract (`docs/03-mcp-contracts.md`). It is returned only when in-app token validation is on and the signing keys cannot be fetched.
- `host.json` sets `extensions.http.routePrefix` to `""` so the well-known address can be served at the root. The health function now declares `api/health`, so `/api/health` does not move; any future HTTP function must give its full route.

The environment is deployed in `EntraBuiltIn` mode, as the successful `ci-cd` run of 2026-10-26 shows ([run 40386017357](https://github.com/saulpatinojr/Proj-Cloud_Architect_Sidekick_MCP/actions/runs/40386017357)). The README, `docs/05` and `docs/06` now describe Entra sign-in for the dev environment and keep the key only for `FunctionKey` mode, including a local `func start`. - Documentation that disagreed with the code: the unit-test count (124, now over 450) in the README, `docs/02`, `docs/05` and `docs/07`, the tool count (27, now 28) in `docs/05` and `docs/08`, `global.json` described as SDK 8 in `docs/02`, the ADR range in `docs/02`, the README documentation index (it missed `docs/10` and `docs/11`), the roadmap still listing the .NET 10 upgrade (done, ADR-0007), and `docs/05` recommending `azd down --purge` (which cannot remove a vault that has purge protection). Counts are no longer written into prose where CI already reports them.

## [0.2.0] - 2026-10-20

### Added
- Agent pack for Claude Code (`.claude/agents/`) and GitHub Copilot (`.github/agents/`).
- Cloud-provider MCP server configurations (Azure, AWS, Google Cloud, Terraform, GitHub) in `.mcp.json`, `.vscode/mcp.json` and `.github/mcp/`.
- Repository community files: CONTRIBUTING, CODE_OF_CONDUCT, SUPPORT, SECURITY, issue and PR templates, CODEOWNERS, CodeQL, labeler and stale workflows.
- VS Code tasks, launch configuration and extension recommendations (`.vscode/`) to build, run and debug the Functions host locally (F5). `.vscode/settings.json` is git-ignored: the Azure Functions extension stores a right-click deploy target there, and deployments go through the CI/CD pipeline's approval gate, what-if preview, health check and smoke test.
- `scripts/setup-adr-deploy.ps1`: one re-runnable step that creates the deploy identity (OIDC federated credential for the subject GitHub reports for the repository, immutable `owner@id/repo@id` subjects included; Contributor plus Role Based Access Control Administrator limited to the roles the template assigns), the protected `adr-dev` environment and the repository variables. Device-code sign-in; no secrets. Safe to re-run: existing repository variables pin the tenant, subscription, region and deploy app (it signs in to that tenant and never creates a second app), auth mode and networking choices are kept, an unconstrained Role Based Access Control Administrator assignment is removed, and every step is read back and verified (`PASS`).

### Changed
- Versioning: the project is pre-production, so the initial release is relabelled `0.1.0` (it was recorded as `1.0.0` but never tagged). The MCP server reports `serverVersion` `0.2.0` (`host.json`).
- Deploy is explicit opt-in: it runs only from `main` when the repository variable `ADR_DEPLOY_ENABLED` is `true`, with a preflight check for the Azure variables; otherwise pushes to `main` emit a `Deploy skipped` notice. The manual-dispatch environment is a fixed choice (no free-text typos creating unprotected environments). Deploy has per-environment concurrency (no cancel-in-progress); both jobs have timeouts.
- A push to `main` that changes only documentation, tests or repository tooling no longer queues a deploy waiting for approval: an unanswered approval held the `adr-dev` concurrency group, so every later deploy queued behind it. Any other path, a change to `ci-cd.yml`, an unknown base commit and a manual dispatch still deploy. The deploy job runs on `ubuntu-24.04` instead of `ubuntu-latest`, so the move to Ubuntu 26 reaches the build job first.
- Test results (TRX + coverage) are uploaded as the `test-results` artifact; `dorny/test-reporter` was removed because it needs `checks: write`, which fork pull requests never get.
- Removed the stale DocGen copy from the unit-test assembly (`tests/AdrMcp.UnitTests/tools/`); `tools/AdrMcp.DocGen` is the only generator.
- Consolidated the duplicate root `adr/` folder into `docs/adr/`, the only ADR location.
- GitHub Actions moved to their Node 24 majors (checkout v7, setup-dotnet v6, upload-artifact v7, gitleaks-action v3, azure/login v3, labeler v7, stale v11, codeql-action v4 — v3 is deprecated in December 2026). Dependabot now groups action updates into one weekly PR.
- Dependabot ignores Microsoft.ApplicationInsights.WorkerService 3.x (it removes types that Microsoft.Azure.Functions.Worker.ApplicationInsights 2.x loads, so the worker would crash at startup) and never updates the `samples/evidence` demo fixture.
- Removed the unused NSubstitute test dependency.
- CodeQL drops results located in source-generated code (`obj/`, `*.g.cs`, e.g. `RegexGenerator.g.cs` from `[GeneratedRegex]`) before uploading the SARIF, under the explicit category `/language:csharp`. All queries still run on handwritten code. The switch from the default category left the old configuration's alerts open on `main` until that configuration was deleted.
- CodeQL excludes `cs/linq/missed-where` and `cs/linq/missed-select` (`.github/codeql/codeql-config.yml`): style suggestions to rewrite a `foreach` as LINQ, not defects. Every security query and every other quality query still runs.
- `samples/evidence/package.json` (detector demo fixture, never installed) moves `vitest` to `^5.0.5`, which closes the critical Dependabot alert for Vitest UI file read on Windows (< 3.2.6).
- Runtime moves from .NET 8 to .NET 10 (LTS) ahead of .NET 8 end of support on 2026-11-10 (ADR-0007, Accepted): `net10.0`, SDK 10.0.1xx, and the Flex Consumption runtime version is now the `functionsDotnetVersion` Bicep parameter (default `10.0`).
- Safety rule SR-EOL-001 is date-aware for .NET: it compares official end-of-support dates (.NET Core 2.1 to .NET 10) with the review date, so it flags .NET 8 and 9 as end of life from 2026-11-11. It also raises a Medium warning in the 90 days before end of support, and now matches `dotnet 6`, `net8.0` and `netcoreapp3.1`.

### Fixed
- IaC drift: the Bicep/Terraform resource-block parser now skips comments and handles escapes, Bicep `'''` strings and quotes inside `${...}` interpolation. An apostrophe in a comment (`// don't …`, `# it's …`) or a string ending in `\\` used to make one resource swallow the next, so a non-compliant resource could be reported Compliant.
- Evidence loading and the maintenance timer still skip a failing file or tenant, but no longer swallow the caller's cancellation (a cancelled load returned a partial evidence set as if complete; shutdown was logged as a failure per tenant).
- CodeQL quality findings: removed discarded Cosmos `QueryDefinition`s, disposed the finding upsert stream and response, replaced a 15-clause auth normalisation ternary with an ordered table, and tidied test disposables.
- `scripts/*.sh` are committed as executable. azd runs the `postprovision` hook as `./scripts/postprovision.sh`, which failed with "Permission denied" (exit 126) on the first adr-dev provision after every resource had been created. `.gitattributes` keeps `*.sh` at LF line endings so a commit from Windows cannot break the hook either.
- CI was red since the initial commit: Azure.Storage.Blobs 12.30.1 sends API version 2026-10-06, which Azurite rejects. CI now runs Azurite 3.37.0 with `--skipApiVersionCheck` and sets `ADR_TEST_REQUIRE_AZURITE=true`, so Azurite tests fail instead of skipping. Local instructions add the same flag.
- Repository links (badges, clone instructions, issue-template contact links) now point to `saulpatinojr/Proj-Cloud_Architect_Sidekick_MCP`.
- First deployment: `scripts/postprovision.sh` no longer treats a 403 (Key Vault role still propagating) as "secret missing". It retries with backoff and creates `principal-hash-salt` only after Key Vault answers SecretNotFound, so an existing salt is never overwritten. The deploy job retries `azd deploy`, waits for `/api/health`, and polls for the `mcp_extension` key before the smoke test.
- The deploy job's plan step is now `azd provision --preview`, so the what-if resolves `infra/main.parameters.json` exactly as `azd provision` does (it previously omitted the deployer role assignments and Defender settings).
- In Entra mode `/api/health` returns 503 when the worker does not see App Service Authentication, so a deployment that would reject every call fails the deploy job instead of going green.
- Entra tenants can now be configured in Azure: `Auth:Tenants:n:{Id, MapTo, Workspaces}` works as Linux app settings, unlike the GUID-keyed `Auth:TenantWorkspaces`/`Auth:TenantMap` (Linux setting names allow only letters, digits and `_`). Previously every Entra tenant got only the `default` workspace, and the maintenance timer never covered Entra tenants. Bicep now enrolls the deployment tenant, so the app also refuses other tenants (defence in depth behind the edge checks). Startup fails on a tenant ID that is not a GUID or appears twice (in any GUID spelling), on two tenants resolving to one ADR tenant ID (they would share a partition), and on tenant or workspace IDs outside the identifier rule. `Auth:Tenants` and `Auth:TenantMap` apply to Entra principals only; the FunctionKey binding still uses `Auth:TenantWorkspaces` alone.
- Worker telemetry: the isolated worker's Application Insights SDK now authenticates with the app's managed identity (read from `APPLICATIONINSIGHTS_AUTHENTICATION_STRING`); with local authentication disabled on Application Insights it was previously rejected, and only host telemetry arrived.
- Cosmos DB: `enableAutomaticFailover` is set explicitly (`true`, matching the deployed account). The template omitted it, so the what-if plan showed `true => false` on every deploy and a full re-provision would have turned it off. No runtime effect: a serverless account runs in a single region. `defaultIdentity`, `analyticalStorageConfiguration` and `enablePerRegionPerPartitionAutoscale` are pinned to the account's values for the same reason (a what-if confirmed no change), so the only account line left in the plan is the read-only `sqlEndpoint`.

### Security
- `authMode=EntraBuiltIn` now deploys App Service Authentication (`authsettingsV2`: Entra provider, require authentication, 401, only the client apps in the new `entraAllowedClientIds` parameter), `WEBSITE_AUTH_AAD_ALLOWED_TENANTS` and `WEBSITE_AUTH_PRM_DEFAULT_WITH_SCOPES` from the new `entraClientId` parameter. The deployment fails without both, and the deploy job asserts an unauthenticated MCP call gets 401. Previously the MCP webhook became `Anonymous` with no authentication in front of it until someone configured it by hand.
- In Entra mode the server rejects every request unless App Service Authentication is enabled (`WEBSITE_AUTH_ENABLED`), so a disabled or drifted configuration cannot turn a forged `X-MS-CLIENT-PRINCIPAL` header into access.
- An Entra principal without a mapped app role now gets no access (`Auth:DefaultRoleWhenNoAppRoles` defaults to `None`, was `Reader`), so every caller needs an assigned app role. Set it to `Reader` to restore the old behaviour.
- `scripts/postprovision.sh` passes the generated salt to `az` through a private temporary file instead of the command line, and fails fast with a network-specific message when the vault firewall or private endpoint blocks the deployer. The example local salt is now too short for durable persistence, so it can never be reused in Azure.
- With durable persistence the app refuses to start when `Adr:PrincipalHashSalt` is the default placeholder, shorter than 32 characters, or an unresolved Key Vault reference, instead of silently hashing principals with a guessable salt.
- Replaced the broken `dotnet list package --vulnerable` step (it printed `MSB0001`, exited 0 and could never fail) with NuGet Audit in `Directory.Build.props` (`NuGetAuditMode=all`, `NuGetAuditLevel=low`). In CI, NU1901–NU1904 are errors, so restore fails on any known vulnerable direct or transitive package.
- Least-privilege workflow token permissions: `{}` at workflow level; `build-test` gets `contents: read` and `pull-requests: read`, `deploy` gets `contents: read` and `id-token: write`.
- Non-GitHub actions (gitleaks-action, Azure/setup-azd, azure/login) are pinned to commit SHAs; the deploy job can mint Azure tokens. Gitleaks now runs before any pull-request code. NuGet Audit fails closed when vulnerability data is unavailable (NU1900/NU1905), and a new CI step scans the Functions host-extension packages (generated `WorkerExtensions` project), which NuGet Audit settings never reach.
- Manually dispatched runs (the deploy path) scan the full git history with gitleaks and failed on 8 false positives in the initial commit (public role IDs, the redactor's replacement text, a sample idempotency key, and the secret-scanner test's deliberate fakes). They are baselined in `.gitleaksignore` by exact fingerprint, and the file is CODEOWNERS-protected.
- The smoke test reads the function key from `ADR_MCP_KEY` and the Entra token from `ADR_MCP_BEARER`, so neither appears on the command line; Azurite in CI binds to `127.0.0.1` and readiness waits for an HTTP answer.
