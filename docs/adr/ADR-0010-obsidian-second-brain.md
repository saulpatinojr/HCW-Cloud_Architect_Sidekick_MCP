# ADR-0010: An Obsidian vault as optional context for the ADR server, through a standalone local MCP server

- Status: Proposed (drafted 2026-10-28 at the owner's request; the owner answered the four questions in "Owner decisions" the same day; the owner chose Route A for phase 2 on 2026-10-28; the owner moves the status to Accepted after the gates below pass)
- Date: 2026-10-28
- Owners: Platform architecture
- Tags: obsidian, context, mcp, evidence, local

## Context
The owner keeps a "second brain" in Obsidian (a note-taking app whose vault is a folder of Markdown files on the owner's machine) and wants its notes available as context when working with the ADR server ("Architecture Sidekick"). Two requirements were stated on 2026-10-28:

1. There must be an option to use the vault together with the ADR server.
2. The vault integration must also work on its own, well, without depending on the ADR server; and the ADR server must keep working without the vault.

**Facts that shape the design:**
- The ADR server runs on Azure Functions and reaches only what is in Cosmos DB, Blob Storage and the MCP request. It cannot read a folder on a laptop, and [docs/04](../04-security-threat-model.md) says it should not be able to.
- A vault holds personal material next to work notes. Anything that leaves the machine must be chosen deliberately.
- [CLAUDE.md](../../CLAUDE.md): human-owned ADR fields are never written by analyzers; anything inferred is capped at confidence 0.6 and labelled `Inferred`; tenant and workspace come from the principal, never from arguments.
- The server already has an evidence path (`file_upload_request`, `file_register_upload`, `evidence_attach`) with secret scanning, tenant isolation and a size cap, and a memory path (`decision_memory_search`) over `IMemoryRepository`. [ADR-0006](ADR-0006-deterministic-first-analysis.md) keeps analysis deterministic first.
- MCP clients can connect to several servers at once. Claude Code, Claude Desktop and VS Code can reach a server on the same machine (stdio); Claude.ai in a browser cannot.
- The vault is synced with Obsidian Sync (Obsidian's own end-to-end encrypted sync service) and used on more than one machine. Obsidian Sync carries ordinary files in the vault; it does not carry hidden folders other than `.obsidian` unless told to, so a setting that must follow the vault belongs in an ordinary file.
- Obsidian ships a headless Sync client, **Obsidian Headless** (open beta): `npm install -g obsidian-headless`, an active Sync subscription, `ob login`, `ob sync-setup` (the vault's end-to-end encryption password is given here or prompted), `ob sync-config --mode pull-only --excluded-folders <list>` to set the sync mode and the exclusions, then `ob sync --continuous` (which itself takes only `--path` and `--continuous`). It keeps "the same encryption and privacy protections as the desktop app, including end-to-end encryption", is meant for "CI pipelines, agents, and automated workflows", and must not run on the same device as the desktop app ([Headless Sync](https://obsidian.md/help/sync/headless), read 2026-10-28). So a host that holds the Sync credentials and the vault password can keep a decrypted copy of chosen folders without any phone or laptop pushing anything.

## Decision
Two pieces, each useful alone, joined only by a setting that is off by default.

1. **A standalone vault MCP server (`obsidian-vault-mcp`)**, a small local process that reads the vault folder directly. It needs neither Obsidian running nor an Obsidian plugin. Read-only tools: `vault_search` (keywords over a folder allow-list), `vault_note_get` (one note, truncated excerpt), `vault_backlinks` (notes that link to a note), `vault_tags` (notes with a tag). **It has no write tool, by the owner's decision**; it never creates, edits or deletes a file in the vault. It has no dependency on this repository's code and ships with its own tests. It lives in this repository under `src/VaultMcp/` with its own solution file (`VaultMcp.sln`), because phase 2 shares the Bicep modules, naming tests and CI shape; `AdrMcp.sln` never references it, so the ADR server's build and tests are unaffected.
   - **Clients:** Claude Code and Claude Desktop (owner's decision). Both run on the owner's machines and speak to the server over stdio. Other local clients (VS Code, Codex, Kiro) can use it too, but are not tested; Claude.ai in a browser is out of scope.
   - **Settings that follow the vault:** the folder allow-list, the context tag and the excerpt limit live in one ordinary Markdown note at the vault root, `adr-sidekick.md`, as front matter, so Obsidian Sync carries them to every machine. The only per-machine setting is the vault path, given in the client's MCP configuration. A machine with no `adr-sidekick.md` gets an empty allow-list: nothing is readable until the note exists.
2. **Integration level A (no server change):** the client connects to both servers, and the `adr-author` and `drift-investigator` agents may cite vault notes in the Context and Rationale they draft. The citation names the note path; the ADR server never sees the vault.
3. **Integration level B (opt-in, server-side):** notes the owner tags (default tag `#adr-context`) inside allow-listed folders are uploaded as evidence through the existing upload path, by a small sync command (not by the vault server, which stays read-only and has no network access to the ADR server), so the existing secret scanner, size caps and tenant isolation apply unchanged. Evidence kind `note`. The server treats such evidence like any other: detectors may read it; the result is `Inferred`, confidence ≤ 0.6. The sync command is just another MCP client of the ADR server: it signs in with the owner's Entra identity through the pre-registered public client of [ADR-0008](ADR-0008-entra-oauth-sign-in-for-mcp-clients.md), sends that bearer token on every call, and the ADR server resolves tenant and workspace from the signed-in principal exactly as it does for every other client. Its inputs are exactly three, all on its command line so every run is explicit: the vault path, the allow-list and the ADR server URL. It has no tenant or workspace argument, reads no configuration file and holds no key of its own. With the chosen clients, level A already covers the stated need; level B is built only if the owner later wants server-side analysis to see notes.
4. **The switch.** Level A is on when the client's MCP configuration lists the vault server, and off when it does not. Level B is on only when the sync command is run with an explicit allow-list and the ADR server URL; the ADR server has no setting for it and does not know whether a vault exists. With both off, both pieces behave exactly as before.
5. **Never:** a vault note writes an ADR field. A change the owner wants from a note goes through `adr_propose_change` and a human approval, like every other change.

## Rationale
- Reading the vault locally keeps personal material on the machine by default and makes the vault tool useful to any MCP client, with or without this server (requirement 2).
- Reusing the upload path for level B means no new trust boundary, no new scanner and no new storage: the vault is just another evidence source (requirement 1), and `HumanOwnedFieldProtectionTests` keep applying.
- A separate process with no shared code is the simplest way to guarantee that neither piece can break the other.

## Considered alternatives
- **The ADR server reads the vault through Obsidian Sync, OneDrive or a git remote.** Rejected: it would put a copy of the whole vault, personal notes included, within reach of a cloud service, and adds credentials to rotate.
- **An Obsidian community plugin that calls the ADR server.** Rejected for now: it depends on Obsidian running, on plugin API changes, and it would be the only MCP client that cannot sign in with Entra ID the way the others do ([ADR-0008](ADR-0008-entra-oauth-sign-in-for-mcp-clients.md)).
- **One combined server.** Rejected: it breaks requirement 2 in both directions.
- **A write tool (for example, drop a note into an `Inbox/` folder when an ADR is accepted).** Rejected by the owner on 2026-10-28: the vault stays read-only. Revisit as its own ADR if the need appears.
- **Per-machine configuration files for the allow-list.** Rejected: two machines would drift apart silently. A note inside the vault is synced by Obsidian Sync with the rest.

## Consequences
- A second server to install and update on each machine; `.mcp.json` and `.vscode/mcp.json` gain an optional entry.
- Claude.ai in a browser gets no vault access (level A needs a local server). It still benefits from level B evidence.
- Level B uploads count against the evidence size cap and the storage cost like any file.
- Level B only: a new evidence kind `note` and, if the owner wants it, a small `IEvidenceSetProvider` filter so drift detectors can be told to ignore notes.
- The vault server is read-only, so a note it shows can be stale by the time Obsidian Sync catches up on another machine; the excerpt carries the file's modified time so the reader can tell.

## Owner decisions (2026-10-28)
1. **Standalone in both directions:** the vault server works without the ADR server, and the ADR server works without the vault.
2. **Clients:** Claude Code and Claude Desktop, and (added later the same day) **the Claude app on the phone**. The phone is phase 2 below.
3. **Sync:** Obsidian Sync, more than one machine. Hence the in-vault settings note.
4. **Read-only.** No write tool.
5. **Phase 2 route: Route A**, Obsidian Headless in Azure (decided 2026-10-28). Route B stays written up as the fallback, used only if the Headless beta fails the verification items below (nested exclusions, Linux behaviour, a note edited on the phone arriving in the container).

## Phase 2: the phone (cloud lane)
The Claude app on a phone talks only to remote MCP servers, through the same connectors as Claude.ai in a browser. So for the phone the vault server must run in Azure, and a decrypted copy of the allow-listed folders must be there too. Obsidian Sync is end-to-end encrypted, so Azure cannot read the Sync service itself; something that holds the vault password has to produce the copy. Two routes were weighed; the owner chose Route A (decision 5), and Route B stays as the fallback:

- **Route A, recommended: Obsidian Headless in Azure.** One always-on container (Azure Container Apps) runs `ob sync-config --mode pull-only --excluded-folders <list>` once, then `ob sync --continuous`, into a mounted Azure Files share; the same vault server as phase 1 reads that folder (the phase 1 local-folder store, served over the HTTP transport instead of stdio). The exclusion list is derived from `adr-sidekick.md` so that nested allow-list entries keep their phase 1 meaning: every folder whose subtree holds no allow-listed folder is excluded at the shallowest level. For `allow: [Work, Projects/Cloud]` that is every top-level folder except `Work` and `Projects`, plus every sibling of `Cloud` inside `Projects`; nothing the allow-list denies is synced, and nothing it allows is dropped. Whether `--excluded-folders` accepts nested paths such as `Projects/Personal` is **to verify** on the beta; if it does not, Route A restricts the allow-list to top-level folders and `adr-sidekick.md` documents that limit. No plugin on any device and no second sync product: Obsidian Sync itself delivers the notes, from the phone and the laptops alike. What it costs: the Sync account credentials and the vault's encryption password live in Key Vault and are handed to the container at start; that container holds a decrypted copy of the synced folders, so the owner accepts that one Azure host is trusted with them (the share is private, encrypted at rest, reachable only by the container's identity); Headless is an open beta, Obsidian's page says to back up first, and the file-creation-time addon is Windows and macOS only (sync works without it on Linux). Because it is an exclusion list, a folder created later is synced until the list is regenerated, so the `sync-config` step is re-run whenever `adr-sidekick.md` changes; the server's own allow-list still refuses such a folder through the tools in the meantime.
- **Route B: a sync plugin on the phone.** An Obsidian community plugin (`Remotely Save` is the usual one) pushes the allow-listed folders to a storage account, and a Functions app with the MCP extension reads that container through a Blob binding of the same core. Whether the plugin writes to Azure Blob Storage directly, and in its free tier, is **to verify** against its current backend list; the fallback is OneDrive in the same tenant read through Microsoft Graph. Every device pushes its own edits, so the phone and each laptop need the plugin.

Route A is recommended: one sync product instead of two, nothing to install on any device, and the vault server stays the code phase 1 ships. Its one real cost, a trusted Azure host holding decrypted notes, exists in Route B as well (the storage account holds the same plain copy).

Design, kept standalone, both routes:
1. **One codebase.** The vault server's core (allow-list, search, excerpts, backlinks, tags) reads an abstract file store. Phase 1 binds it to a local folder over stdio. Route A binds the same local-folder store to the mounted share and serves it over HTTP; Route B adds a Blob store binding, hosted as its own Azure Functions app with the MCP extension, the same stack as the ADR server. Still no write tool in any mode.
2. **Its own resources, named by [ADR-0009](ADR-0009-azure-naming-convention.md)** with workload `vault`: on Route A a Container Apps environment and app plus a storage account with one private file share (for example `ca-vault-dev-scus-01`, `stvaultdevscus01`); on Route B a Function app plus a storage account with one private container (`func-vault-dev-scus-01`). In both: a managed identity, and Key Vault for the Sync credentials and the vault password (Route A) or a plugin credential if one is needed (Route B). It shares nothing with the ADR server at runtime; it shares the Bicep modules, the naming tests and the CI shape, so it lives in this repository under its own solution file that `AdrMcp.sln` never references.
3. **Sign-in:** the same pattern as [ADR-0008](ADR-0008-entra-oauth-sign-in-for-mcp-clients.md), applied to a second server with its own identity. The vault server gets its own app registration (its client ID is the token audience; its own `user_impersonation` scope), one app role `Vault.Reader` with the owner as the only assignment, and its own role map (`Vault.Reader` maps to Reader; nothing else maps, so a token without it is refused with 403). The client applications are the same pre-registered ones ADR-0008 allow-lists; each is pre-authorized on the new scope, and Entra asks the user once for consent to it. ADR-0008 itself, and the ADR server's `Auth:AppRoleMap`, are not changed: an ADR server token is refused by the vault server (wrong audience) and the other way round. On Route A the host is Container Apps, whose built-in authentication is the same Easy Auth, but the MCP-specific challenge and protected resource metadata are then served by the app itself (the in-app layer of ADR-0008 becomes the primary one); that this works end to end is **to verify**.
4. **The allow-list still lives in the vault** (`adr-sidekick.md`). The synced copy carries it, so the phone's server and the laptops read the same list. The exclusion list (Route A) or the plugin's folder choice (Route B) limits what leaves the devices; the server additionally refuses anything outside the allow-list, so a misconfiguration leaks nothing through the tools. A plain copy can still sit in the share or the container, which is the owner's private storage, encrypted at rest and readable only by the host's identity.
5. **Freshness:** Route A, as fresh as Obsidian Sync delivers it (continuous); Route B, the last push from a device. Every excerpt carries the file's modified time.

**Progress (2026-10-28):** step 1a, the HTTP host (`VaultMcp.Http`, Locked by default) and its container image, is in `src/VaultMcp/`; step 1b, the Azure template `infra/vault/main.bicep` with the azd project `src/VaultMcp/azure.yaml`, deploys it to Container Apps with the share mounted read-only through the environment's managed identity (SMB OAuth, preview; account key as the fallback), its own registry, Key Vault, Log Analytics and identity, named per ADR-0009 with workload `vault`. The template has been evaluated offline (build, lint, `bicep snapshot` for every region) and not yet provisioned in a subscription. Step 2 (the headless Sync container, a read-write mount of the same share, the secrets in Key Vault) and step 3 (sign-in) are not started.

**Prerequisites before phase 2 can be used:** checklist item F3 in [docs/12](../12-entra-sign-in-checklist.md) (Claude.ai and Desktop sign in through Entra) must pass, because the phone uses the same connector. On Route A, a headless-sync container must be shown to receive a note edited on the phone, and the beta's behaviour on Linux checked; on Route B, the plugin's backend and its mobile behaviour must be verified on the owner's phone. None of this is done. Anthropic's help article on custom connectors, as quoted in the review of the pull request that added this ADR (the article has since moved and could not be re-read on 2026-10-28), says the iOS and Android apps use remote servers already added on claude.ai and cannot add servers themselves; so the phone needs no setup of its own beyond signing in, and the owner confirms that on the phone as part of F3.

**Why not instead:** a cloud-only vault with no Obsidian Sync (rejected: the owner has Sync and uses it between machines; the cloud lane is an export, not a replacement); the ADR server reading the container itself (rejected: breaks standalone in both directions, and mixes personal notes into the ADR server's trust boundary; the existing evidence upload path remains the way notes reach the ADR server, level B); Obsidian Publish (rejected: it makes notes public).

## Gates before this ADR can be Accepted
1. A prototype of the vault server passes its own tests with the ADR server stopped, and its tool list shows only the four read tools.
2. `dotnet test AdrMcp.sln` is green with no reference to the vault server.
3. On a second machine with the vault synced, the same `adr-sidekick.md` allow-list applies without any local setup beyond the vault path.
4. A note outside the allow-list is not returned by `vault_search` or `vault_note_get`.
5. Level B, if built: a note holding a fake secret is refused by the existing scanner on upload.
6. Phase 2: the same tests pass against the phase 2 store (the mounted share on Route A; the Blob backend with Azurite on Route B); an unauthenticated call to the cloud vault server gets 401; the phone signs in and lists the four tools.

## Rollback
Remove the optional `.mcp.json` entry and stop the vault server. Level B evidence is removed with `evidence_remove` like any other evidence. No ADR field was ever written by the integration, so nothing else changes.
